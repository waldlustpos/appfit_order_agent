# 라벨 2장 출력 사고 (2026-08-03, 아오야마점)

공유용 정리. 앞부분(무슨 일 / 왜)은 비개발자도 읽을 수 있게, 뒷부분(근거 / 수정)은 개발자용.

---

## 한 줄 요약

**"응답이 없다 = 인쇄가 안 됐다"로 앱이 잘못 판단해, 이미 프린터로 보낸 라벨을 한 번 더 보냈습니다.** 라벨 자체는 처음부터 정상 출력됐습니다.

## 무슨 일이 있었나

2026-08-03 아오야마점(青山店)에서 주문 **#956 라벨이 2장** 나왔다는 현장 보고가 있었습니다. 그날 로그를 전부 확인해 보니 같은 일이 오전 **09:35 #906**에서도 한 번 더 있었습니다.

빈도는 **그날 출력한 라벨 258장 중 2장(0.8%)**입니다. 나머지 256장은 모두 1.1초 안에 정상 완료됐습니다.

## 왜 2장이 나왔나

1. 앱은 라벨 명령을 프린터로 보낸 뒤, **"인쇄 끝났다"는 응답을 최대 30초 기다립니다.**
2. 이 두 건은 **라벨은 정상적으로 나왔는데 그 응답만 도착하지 않았습니다.** 앱은 30초를 다 기다린 뒤 "인쇄에 실패했구나"로 판단했습니다.
3. 앱이 실패로 알고 **같은 라벨을 다시 보냈습니다.** 그래서 약 31초 뒤 두 번째 장이 나왔습니다.

문제는 2번 판단입니다. 인쇄 명령은 응답을 기다리기 **전에** 이미 프린터로 나가 있습니다. 그러니 "응답이 없다"는 건 "종이가 안 나왔다"가 아니라 **"결과를 모른다"**일 뿐인데, 앱은 이걸 실패로 단정했습니다.

## 부수 피해 — 라벨이 30초 동안 멈춤

응답을 기다리는 30초 동안 **라벨 출력 전체가 멈춥니다.**

- 13:08 건: 다음 주문 #762 라벨이 **33초 늦게** 나왔습니다.
- 09:35 건: 직원이 라벨이 안 나온다고 판단해 **재출력 버튼을 누르고 새로고침을 눌렀습니다**(09:34:56, 09:35:02 조작 기록 있음).

## 현장에서 참고할 점

**라벨이 나오면 바로 떼어 주세요.**

이번 2장 사고의 직접 원인은 아니지만, 별개로 확인된 사실이 있습니다. 앞 라벨을 떼지 않으면
**프린터가 다음 라벨을 인쇄하지 않고 붙잡고 있다가, 떼는 순간 인쇄합니다.** 실기기 테스트에서
안 뗀 채로 두니 다음 라벨이 **19초까지** 밀렸습니다. 그 동안 다른 주문의 라벨도 전부 대기합니다.

프린터가 고장 난 게 아니라 순서를 지키려고 기다리는 것입니다. 떼면 바로 나옵니다.

## 개발자용 — 근거

### 확정된 사실

- 0956은 큐에 **한 번만** 들어갔다 (`인쇄진입` 1회, `NEW_LABEL 완료` 1회, labels=1). 큐 중복·이중 트리거가 아니다.
- 두 장의 정체: `#205` 1차 시도(`실패 (30182ms)`) + `#206` 자동 재시도(성공 1070ms).
  `13:08:23.230 1차실패 → 1.5초 후 재시도` 로그와 정확히 1.5초 뒤의 `#206 출력시작`이 이를 확정한다.
- 30182ms − 30000ms = 182ms. 30000ms는 `QUERY_PRINT_RESULT_TIMEOUT_MS`와 일치 →
  연결·게이트·이미지 전송은 정상 통과했고 `CP_Pos_QueryPrintResult`만 꽉 채워 timeout.

### 실기기 재현으로 확정한 것 (2026-08-03, D2s_KDS_STGL + REXOD)

`INFO_PAPERNOFETCH` 비트 전이를 logcat에 찍도록 하고 테스트 출력을 3회 수행했다.

```
15:09:25.068 #1 출력시작
15:09:25.196   PAPERNOFETCH → 떼어짐/없음
15:09:25.893   PAPERNOFETCH → 안뗌(라벨 대기중)      ← 라벨이 peel 도달 (0.83초)
15:09:26.391 #1 출력끝 (1323ms)                      ← 안 뗀 상태인데 출력끝

15:09:37.170 #2 출력시작                             ← 앞 장 안 뗀 상태에서 발사
15:09:42.365   PAPERNOFETCH → 떼어짐/없음            ← 5.2초 뒤 사용자가 뗌
15:09:42.878   PAPERNOFETCH → 안뗌
15:09:43.335 #2 출력끝 (6165ms)
```

**① 펌웨어 보류는 실재한다.** 앞 라벨이 안 떼어져 있으면 다음 PagePrint를 물고 있다가
떼는 순간 인쇄한다. 소요시간 = 떼기까지 걸린 시간 + 약 1.1초. (별도 테스트에서 19.2초까지 관측)

**② `CP_Pos_QueryPrintResult`는 떼기를 기다리지 않는다.** #1은 `PAPERNOFETCH=안뗌` 상태에서
`출력끝`이 났다. 응답은 인쇄 엔진 완료 시점에 온다.

**③ `INFO_PAPERNOFETCH` 비트는 이 단말에서 정상 동작한다.** 매 인쇄마다 전이가 찍힌다.

### 그래서 이 두 건은 보류가 아니다

③이 사고 로그의 의미를 확정한다.

`실패 (30182ms)`는 `LabelPrinter.printBitmap` 최종 분기까지 떨어졌다는 뜻이고,
그건 그 순간 **`lastInfoPaperNoFetch == false`** 였다는 뜻이다. 비트가 정상 동작하고
status 비콘이 약 2초 주기이므로, 30초 내내 보류 상태였다면 비콘이 열댓 번 도착하는 동안
계속 true로 유지됐어야 한다.

**→ timeout 순간 peel에 안 떼진 라벨이 없었다 = 보류가 아니었다 = 완료 응답이 유실됐다.**

부합하는 정황:
- 재시도(#206)가 **1070ms로 즉시 성공**했다. 보류였다면 재시도분도 함께 막혔어야 한다.
- 현장 확인: "30초 이상 안 떼어진 적은 없는 것 같다"
- 문제의 두 건은 둘 다 **라벨 1장짜리 단일 주문** — 다른 단일 라벨은 예외 없이 ~1.08초인 부류다.

유실 지점은 SDK/펌웨어의 USB bulk-in 응답 경로로 추정한다(자발적 status 비콘이 같은 IN
엔드포인트를 공유). 0.8%라는 산발성도 이에 부합한다. 앱에서 없앨 수 있는 성질은 아니다.

### 배제된 가설

| 가설 | 판정 | 근거 |
|---|---|---|
| 비콘(StatusEvent) 미수신 | ✗ | 12:11 `ERROR=0x0004[NoPaper]`, `ERROR 해제` 로그 정상 수신 |
| `CP_Pos_QueryPrintResult` 자체 불량 | ✗ | 하루 250여 회 정상(~1070ms) |
| PrintedEvent 콜백 미등록이 근본 원인 | ✗ | 미등록 상태에서도 ACK가 정상 도착 |
| 앞 라벨 미제거 → 펌웨어 보류 | ✗ (이 두 건 한정) | timeout 시점 `paperNoFetch=false` + 비트 정상 동작 확인. **보류 자체는 실재하며 평소 1~19초 지연의 원인이다** |

### 기존 가드는 고장이 아니었다

`LabelPrinter.java`의 `INFO_PAPERNOFETCH` 무한 대기 가드는 정상 동작한다.
사고 때 안 걸린 것은 고장이 아니라 **그 상황이 보류가 아니었기 때문**이다.

빠져 있던 것은 "보류도 아닌데 완료 응답이 없는" 케이스 하나뿐이고,
그것이 이번에 추가한 `RESULT_SUBMITTED_NO_ACK` 이다.

## 수정

**원칙: PagePrint를 발사한 뒤의 무응답은 재시도하지 않는다.**

네이티브 `LabelPrinter.printBitmap`의 반환을 bool → 3분류로 확장했다.

| 결과 | 의미 | 재시도 |
|---|---|---|
| `RESULT_SUCCESS` | 인쇄 완료 확인 | — |
| `RESULT_RETRYABLE` | PagePrint 발사 **전** 실패 (연결오류·펌웨어 ERROR·용지없음 취소) | O |
| `RESULT_SUBMITTED_NO_ACK` | 발사 **후** 무응답 | **X** |

`submittedNoAck`은 성공으로 취급하고 재발사하지 않는다. 대신 `LabelAckTimeoutException`으로
Sentry에 집계해 **매장·기기별 발생 빈도**를 추적한다(0.8%가 이 기기만의 문제인지 판별용).

추가로 timeout 시점에 `CP_Printer_GetPrinterPrintedInfo`로 인쇄 매수를 조회해,
값이 증가했으면 ACK 없이도 인쇄 성공으로 확정한다(단말이 이 API를 지원하는 경우).

실패 로그도 사유를 남기도록 바꿨다. 기존 `실패 (30182ms)`로는 timeout인지 구분이 안 됐다:

```
실패 [ACK timeout 30000ms — 재시도 금지] (30182ms) pg=41→41 비콘[paperNoFetch=false …] 동기[err=0x0000 info=0x00C0] portOk=true
```

## 후속 검토 (이번 수정 범위 밖)

**보류 중 라벨 큐가 최대 30초 멈추는 문제.** 사고와는 별개이고, 보류는 펌웨어가 순서를
지키는 정상 동작이라 무리해서 없앨 이유는 약하다. 다만 `INFO_PAPERNOFETCH` 가 정상 동작함이
확인됐으므로, 필요하면 진입 게이트에서 이 비트를 보고 대기 상태를 UI로 알리는 선택지가 있다
(현재는 게이트 조건에서 의도적으로 제외돼 있다).

**`QUERY_PRINT_RESULT_TIMEOUT_MS` 30초 유지.** 보류가 실재하므로 timeout 을 줄이면 아직
인쇄되지 않은 페이지를 "응답 없음"으로 넘기고 다음 라벨을 발사하게 되어 펌웨어 버퍼에 쌓인다.
중복은 안 나지만 출력 순서 체감이 나빠질 수 있어 현행 유지가 안전하다.

**발생 빈도 관측.** `LabelAckTimeoutException` Sentry 집계로 0.8%가 이 기기·매장에 한정된
현상인지 확인한 뒤 다음 판단을 한다.

## 후속 경과 (2026-08-07)

### 수정은 운영에서 작동했다

2026-08-04~06 Sentry 16건(TPCP00001 8 · PAIK00002 8) **전부 `attempt=1`** —
`submittedNoAck` 에서 재발사가 한 번도 없었고 중복 인쇄 재발 보고도 없다.
`test/core/label_print_retry_test.dart` 가 고정한 "submittedNoAck ⇒ dispatch 1회" 불변식이
실운영에서 실증됐다.

### 위 "발생 빈도 관측" 은 현 구성으로 답할 수 없다

두 가지 이유로 이 숙제는 그대로는 성립하지 않는다.

**① 대조군이 없다.** 실 운영 매장은 2곳이 전부이고 둘 다 D2s_KDS_STGL + REXOD 만 쓴다.
"D2s_KDS_STGL 16/16, 다른 기종 0건" 은 기기 고유 현상의 근거가 **아니다** — 다른 기종은
라벨을 안 찍으니 0건인 선택 효과다. 다른 조합이 운영에 투입되기 전까지는 판별 불가다.

**② 비율을 낼 수 없었다.** 이벤트에 분모(총 라벨 수)가 없었고, `MonitoringService.captureError`
가 `runtimeType` 기준 **5분 쿨다운**을 걸어 버스트는 breadcrumb 으로만 남았다. 즉 이벤트
개수는 하한선일 뿐이다. 본문 "258장 중 2장(0.8%)" 은 기기 로그 파일을 사람이 하루치 센 값이고,
Sentry 로는 재현할 수 없는 수치였다.

### 그래서 계측을 먼저 넣었다 (Phase A)

- **네이티브 진단 스냅샷을 이벤트에 첨부.** `diagnosticSnapshot()` 이 이미 만들던 값(`portOk`·
  비콘 `age`·`err`·`pg`)이 기기 로그로만 나가고 있었다. `LabelPrinter.consumeLastAckDiagnostic()`
  + MethodChannel `getLastLabelAckDiagnostic` 으로 Dart 가 읽어 `extras['diagnostic']` 에 싣는다.
  `printLabel` 의 int 반환 계약은 건드리지 않았다(Map 으로 바꾸면 `invokeMethod<int>` 타입
  캐스트 실패가 `on PlatformException` 에 안 잡혀 3분류 경로를 흔든다).
- **분모·누적 카운터.** `labelsAttempted` / `ackTimeouts` 를 모든 이벤트에 싣는다. 비율을
  이벤트 하나에서 읽을 수 있고, 연속한 두 이벤트의 `ackTimeouts` 차이가 그 사이 실제 발생
  건수라 쿨다운에 먹힌 건수도 복원된다.

**비콘 `age` 가 핵심 판별자다.** timeout 순간 비콘이 살아 있었으면 유실된 것은 print-result
응답 하나뿐이고, 비콘도 함께 끊겼으면 IN 엔드포인트 전체가 멎은 것이라 원인이 다르다.

검증: 실기기(D2s_KDS_STGL `DK1925AJ40349` + REXOD)에서 `QUERY_PRINT_RESULT_TIMEOUT_MS` 를
임시로 300ms 로 낮춘 디버그 빌드로 경로를 강제 발생시켜 Sentry 도달까지 확인(원복 완료).

```
09:05:16.230 #1 [0005] 출력시작
09:05:16.926 #1 [0005] 실패 [ACK timeout 300ms — 재시도 금지] (691ms) pg=0→0
             비콘[paperNoFetch=false … err=0x0000 age=104ms] 동기[…] portOk=true
09:05:17.016   PAPERNOFETCH → 안뗌(라벨 대기중)      ← 라벨은 실제로 나왔다
```

`출력시작` 이 1회뿐이고, timeout 0.09초 뒤 라벨이 peel 에 도달했다 — **"timeout ≠ 안 나왔다"**
라는 이 문서의 핵심 전제가 실기기에서 다시 확인됐다.

## 후속 2 — 실매장 로그가 밝힌 것 (新橋店 2026-08-07)

Phase A 배포 전이지만 진단 스냅샷은 이미 들어 있어(852ac44), 같은 날 올라온 Sentry 2건을
로그로 갈라볼 수 있었다. **두 건은 서로 다른 현상이었다.**

- `#40 [0817]` — `recvIdle=true printIdle=true`(프린터 idle) · `pg=7→8`(카운터 증가) ·
  `age=1689ms`(비콘 생존) → **응답만 유실**. 라벨은 나왔고 프린터는 놀고 있었다.
- `#111 [0029 1/2]` — `recvIdle=false printIdle=false`(30초 시점에도 작업 중) ·
  이웃이 13.0/11.6/15.5초 → **정체 tail**. 응답 유실이 아니라 차례가 안 왔을 뿐.

두 건 모두 라벨은 물리적으로 출력됐다(페이지 카운터 연쇄로 확정). 재시도 금지 판단은 옳았다.

### 전제 정정 — 라벨을 늦게 떼는 것은 정상 운영이다

같은 로그에서 라벨 211장 중 **11장이 30초를 소진**했다(떼기대기 9 + ACK timeout 2).
23%(48장)가 10초 이상 걸렸고 떼기까지 최장 69초였다.

처음엔 이것을 "줄여야 할 큐 정지"로 봤으나 **틀렸다.** 앞 라벨을 안 떼면 펌웨어가 실제로
인쇄를 하지 않으므로 그 시간은 낭비가 아니라 기다려야 하는 시간이고, 러시아워에 음료를
만들고 나중에 일괄로 떼는 것은 **정상 작업 흐름**이다. 앱이 적응해야 할 입력이지 고칠
대상이 아니다.

### 그래서 한 것 — 완료 판정을 다중 신호로

고칠 수 있는 것은 보류가 아니라 **"이미 나왔는데 응답이 없는"** 경우(`#40` 유형)뿐이다.
`QueryPrintResult` 단일 의존을 벗어나 **PAPERNOFETCH 상승 edge** 를 독립 완료 신호로 추가했다.
설계·근거·실측은 [PRINTER_FLOW.md §3.2](PRINTER_FLOW.md) 에 정리했다.

이로써 `LabelAckTimeoutException` 은 **두 신호가 모두 없는** 진짜 이상에만 남는다 —
지금까지처럼 성격이 다른 사건을 담는 잔여 범주가 아니다.

### 다음 (미착수)

**`feedToTear` 순서 교정은 우선순위를 내렸다.** `PagePrint` 와 `QueryPrintResult` 사이에
있어 공유 IN 엔드포인트 간섭 가설과 정합하지만, 두 플랫폼은 이 순서 말고도 떼기 대기
시점·ACK 획득 방식이 함께 달라 "Windows 는 멀쩡하다"가 근거로 약하다
([PRINTER_FLOW.md §3.1](PRINTER_FLOW.md)). 게다가 다중 신호가 `#40` 유형을 정상 완료로
흡수하므로 남는 잔여부터 다시 세는 것이 순서다. 배포 후 `via=` 분포로 판단한다.
