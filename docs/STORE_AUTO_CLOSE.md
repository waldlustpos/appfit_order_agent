# 매장 자동 CLOSED (서버측 dead-man switch) 제안

**상태**: 제안 단계. 앱 구현 없음, 서버 결정 대기.
**대상 독자**: AppFit 백엔드 담당.

## 1. 문제

매장 단말(주문 에이전트)이 꺼졌는데 서버의 매장 상태가 `OPEN` 으로 남으면, 키오스크·모바일 주문이 계속 들어오고 **아무도 받지 못한다.** 손님은 주문·결제가 됐다고 알고 있고 매장은 그 주문의 존재를 모른다.

앱은 종료 경로마다 `PUT /v0/shop/{shopCode}/operating-status` 로 `CLOSED` 를 보내지만, **보낼 수 없는 종료가 더 많다.**

## 2. 클라이언트가 덮는 범위 — 그리고 못 덮는 범위

| 종료 경로 | 앱이 CLOSED 를 보내는가 | 근거 |
|---|---|---|
| 종료 버튼 | O | `home_screen._exitApp` |
| 로그아웃 | O | `home_screen._handleLogout` |
| 정상 전원종료(전원버튼) | O | `ShutdownSalesOffBridge` (아래 §3 실측) |
| 앱 스와이프 종료 / Activity 파괴 | O | 라이프사이클 `detached` |
| **정전 · 플러그 뽑힘** | **X** | 전기가 없다 |
| **전원버튼 강제 리부트(하드 리셋)** | **X** | 커널이 즉시 내려간다 |
| **네트워크 단절** | **X** | 보낼 경로가 없다 |
| **OS 의 프로세스 kill** | 사실상 X | 실행 기회가 보장되지 않는다 |

아래 4개는 **원리적으로** 클라이언트에서 감지·전송할 수 없다. 매장 현장에서 흔한 쪽이 오히려 이쪽이다(멀티탭 스위치, 정전, 인터넷 장애). 서버가 판단하는 수밖에 없다.

## 3. 클라이언트 쪽은 할 수 있는 만큼 했다 (실측)

2026-09-04, 실제 프레임워크 종료 시퀀스에서 측정:

```
D3 MINI  (Android 13, SDK 33)  net=wifi/internet=true,validated=true  salesOff=ok(97ms)  totalMs=101
T2mini_s (Android 7.1.1, SDK 25) net=wifi/internet=true,validated=true  dns=14ms tcp=12ms dart=3ms totalMs=39
```

전원종료 시점에도 네트워크는 살아 있고(AOSP `ShutdownThread` 가 라디오를 브로드캐스트 **이후에** 내린다), 인증 포함 PUT 왕복이 100ms 안에 끝난다. 즉 §2 의 O 항목은 신뢰할 수 있다. 남은 건 X 항목뿐이고, 그게 이 문서의 요청 사항이다.

## 4. 제안

**앱의 WebSocket 세션이 N분 이상 부재하면 서버가 해당 매장을 `CLOSED` 로 내린다.**

### 이미 있는 재료

- 앱은 `shopCode` 단위로 WebSocket 을 유지한다 (`appfit_core` `AppFitNotifierService`). 서버는 어느 소켓이 어느 매장인지 이미 안다.
- 앱은 60초 주기 heartbeat 로 ghost connection 을 감지한다. 즉 살아 있는 단말은 최소 그 주기로 존재를 증명한다.

새 엔드포인트도, 앱 변경도 필요 없다. 서버가 이미 가진 연결 상태만 판정에 쓰면 된다.

### N 값 — 최소 10분 권장

앱의 재연결 정책이 판정 하한을 정한다.

- 빠른 백오프 5회: 3 → 6 → 12 → 24 → 48초 (누적 약 1.5분)
- 이후 **포기하지 않고** 300초(5분) 간격 slow retry 로 무한 재시도

즉 "링크는 살아 있는데 상위 경로만 죽은" 장애에서 앱은 최대 5분 간격으로 돌아온다. N 을 5분 이하로 잡으면 **잠깐 끊긴 정상 매장을 닫아 버린다.** 10분이면 slow retry 를 2회 놓친 셈이라 안전하다.

### 반드시 함께 처리할 것 — 재연결 시 상태 밀어주기

앱은 영업 상태를 **낙관적으로** 갱신한다(`store_provider.setIsOpen`). 서버가 매장을 닫았는데 앱 화면은 "영업중"으로 남으면, 점주는 열려 있다고 믿고 손님은 주문이 안 되는 최악의 불일치가 된다.

→ 서버가 자동 CLOSED 를 적용한 매장의 소켓이 재연결되면, **연결 직후 현재 매장 상태를 앱에 내려보내야 한다.**

### 자동 CLOSED 이후의 복귀

앱은 다음 기동 시 로컬 토글(`KEY_ORDER_ON`)로 서버 상태를 복원한다(`home_screen` 앱 실행 경로). 즉 단말이 돌아오면 매장은 스스로 다시 열린다 — 서버가 닫아둔 것을 사람이 손으로 되돌릴 필요는 없다.

## 5. 이 제안이 대체하지 않는 것

클라이언트 경로(§2 의 O)는 그대로 둔다. 서버 판정은 **N분 지연**이 있고, 그 사이에 들어온 주문은 여전히 미접수로 남는다. 정상 종료를 즉시 반영하는 클라이언트 경로와, 비정상 종료를 늦게라도 잡는 서버 경로는 서로를 대체하지 않는다.
