## ⚠️ 착수 전 전제 두 개가 모두 기각됐다

**① "XD5-40d 표준기는 필러 미장착"** — 드라이버 javadoc 이 그렇게 단언하고 있었고, 그 한 줄이
이 작업의 착수를 한 번 막았다. 그런데 같은 기기의 2026-07-23 실기기 8장 주문 기록
([[project_bixolon_xd5_40d]])이 정반대다 — 라벨마다 떼기대기 진입, 떼는 즉시 다음 장.
**구현 시점의 가정이 실측 뒤에도 주석에 남아 있었다.**

**② "비프음이 안 나니 버저가 없다"** — 판정 자체가 불가능했다. `printBitmap` 이
`synchronized` 인데 완료 폴링이 **내 라벨을 뗄 때까지** 무한 대기해서, 다음 제출이 lock 에
막혀 펌웨어가 "라벨 미회수 + 다음 페이지 대기" 상태에 **한 번도 도달한 적이 없다.**

**Why:** 증상이 관측되지 않는 것은 원인이 없다는 증거가 아니다. 구조가 그 상태의 **발생
자체를 막고 있으면** 관측은 애초에 불가능하다. [[reference_rexod_label_printer_signals]] 의
"관찰 불가한 가드 = 없는 가드" 와 같은 뿌리인데, 이번엔 가드가 아니라 **현상**이 대상이었다.

**How to apply:** 하드웨어/펌웨어 기능의 부재를 결론짓기 전에, 우리 코드가 그 기능이 발현될
조건을 만들어 주고 있는지부터 확인할 것. 그리고 **주석과 실측이 충돌하면 실측이 이긴다** —
이긴 쪽으로 주석을 고쳐 두지 않으면 다음 사람이 같은 벽에 부딪힌다.

## 설계에서 새로 나온 함정 — edge 귀속 레이스

완료 신호를 `peel 상승 edge`(①) / `busy 상승 후 하강`(③)로 이중화했는데, **③으로 곧바로
반환하면 안 된다.** peel 비트가 busy 하강보다 반 박자 늦게 서면 그 edge 가 아직 안 세어진 채
다음 라벨이 `riseBefore` 를 잡고 → **앞 라벨의 edge 를 자기 것으로 오인**해 인쇄 시작 전에
완료 판정한다. 귀속 어긋남이 이후 라벨로 연쇄한다. → ③은 **한 폴링 더 확인하고** 확정한다.

Caysn 에는 이 문제가 안 보였는데, 거기선 peel edge 가 query 응답보다 150~500ms **먼저** 와서
①이 항상 이겼기 때문이다(경험적으로만 닫혀 있던 것). 신호를 이중화할 때는 **어느 쪽이 먼저
오는지가 귀속의 정확성을 좌우한다.**

## 리셋 금지의 비대칭

`sPeelRiseCount`(카운터)뿐 아니라 `sLastPeelLevel`(레벨 캐시)도 `closeLocked()` 에서
리셋하지 않는다. 레벨을 false 로 되돌리면 재연결 첫 읽기가 **없던 edge 를 만들어낸다.**
놓친 edge 는 busy 신호로 폴백되지만(안전), 만들어낸 edge 는 곧바로 오검출이다 —
**해악이 비대칭이므로 항상 후자를 피한다.**

## 공통화 판단 (사용자 요구: 무리한 공통화 숙고)

두 드라이버는 신호 획득 모델이 다르다(Caysn=SDK 콜백 비콘+블로킹 질의, BIXOLON=200ms 폴링).
**공통 추상 클래스는 만들지 않았다.** 이식한 것은 ①edge 카운터 패턴 ②완료 사유 어휘
(`라벨나옴`/`프린터응답`/`떼기대기`) ③불변식 문구뿐. **grep 키워드가 운영 계약**이라 어휘
통일이 실질 가치다.

## 상태 variant 진단 구멍

BASIC(1바이트 응답)이면 byte1 이 0 패딩이라 떼기대기·busy 게이트가 **영구 no-op** 인데 그
사실이 로그에 없었다 → **"떼기대기 로그가 없다" ≠ "필러가 없다"**. `상태응답=확장/기본` 을
학습 시점에 기록하도록 추가했다. BASIC 에서 신호 ①③이 영영 안 오므로 체류시간 폴백(1초)이
없으면 30초 소진 → 재시도 → **중복 인쇄**가 된다.

## 1차 실기기 — 이상 상태 프레임 `0x5630` (증상 2개가 같은 원인)

8장 주문: 8/8 출력·중복 0, `떼기대기` 3회 정상 진입(9.1/8.0/5.6s) — **메커니즘은 동작.**
그런데 `인쇄중 복구대기 진입 [커버열림] status=0x5630` 이 5회. 비트로 풀면 byte0=0x56 은
"커버열림+헤드과열+리본소진 동시"에 미정의 비트 0x02, byte1=0x30 은 떼기대기 + 미정의 0x10.
ASCII 로 `"V0"` — **상태가 아니라 직전 명령 응답의 잔여**다.

**핵심: 커버열림 오판 하나의 문제가 아니었다.** byte1 의 0x20 이 떼기대기 비트라 edge
카운터에 들어가면 **없던 배출 edge 를 만들어낸다.** 로그 8건이 이 모델과 정확히 일치했고,
결정적 증거는 **`커버열림` 로그 유무와 소요시간의 완벽한 역상관**이었다 — 로그 있음은 전부
2초 이상, 없음은 전부 ~400ms. 신호 ①이 `isRecoverableError` 보다 **앞**이라 유령 edge 가 생긴
회차는 즉시 반환해 커버열림을 아예 로그하지 않기 때문. **두 증상은 같은 프레임의 두 얼굴.**

**How to apply:** 하드웨어 상태 바이트를 비트필드로 파싱할 때 **정의된 비트 마스크 밖의
비트가 서 있으면 그 프레임을 버려라.** "말이 되는 값인가"를 먼저 묻지 않으면, 잘못된 프레임
하나가 서로 무관해 보이는 증상 여러 개로 갈라져 나온다. 그리고 **증상 A 와 증상 B 가
역상관이면 원인이 하나일 가능성이 높다** — 분기 순서가 어느 얼굴을 보여줄지 가른다.

대응: `readStatusLocked` 앞에 프레임 검증(byte0 `0xFC` / byte1 `0xE0` 마스크). 이상이면 최대
3회 재읽기로 잔여를 흘려보내고, 그래도 이상하면 읽기 실패로 넘긴다. **절대 edge 카운터·에러
판정에 먹이지 않는다.** `상태프레임 이상 0xXXXX` 로그로 빈도를 셀 수 있게 했다.

## ★ 2차 실기기 결론 — XD5-40d 는 이 조건에서 비프음이 없다

cold start 8장. `떼기대기` **5회 진입**(= 내 페이지가 펌웨어에 들어간 채 앞 라벨이 필러를
막고 있고, 떼는 즉시 보류 해제·인쇄됨 = 조건 성립의 증거) **그런데 소리 안 남.**
→ **펌웨어가 이 조건에서 buzzer 를 울리지 않는다.** SDK 에 buzzer API 가 없다는 조사와 일관.
`.so` 의 `Buzzer Driver` 섹션은 제품군 공용이라 이 모델 탑재의 증거가 아니었다.

**소요시간이 유령 edge 진단을 확증했다**: 보류 없는 정상 인쇄가 **1.4~1.6초**(#7 1397ms,
#8 1648ms). 1차의 ~400ms 대는 물리적으로 불가능한 값이었다.

**⚠️ 프레임 검증 가드는 아직 발화하지 않았다.** `상태프레임 이상` 0건 = "가드가 잡았다" 가
아니라 **"이번엔 이상 프레임이 아예 없었다"**(발화하면 로그가 남는다). 커버열림 오판 0건도
같은 사실로 설명된다. 1차는 `#12~#19`(오래된 연결), 2차는 `#1~#8`(cold start) — **연결 수명
상관 가능성**. 가드 효과는 재현 시에만 확인된다. 로그가 "고쳐졌다" 를 보여준 것처럼 보일 때,
**가드가 발화한 흔적이 있는지부터 확인할 것.**

무코드로 남은 확인: 진짜 에러(커버 열기/용지 제거)에서 소리가 나는지 → 나면 버저는 있고
이 조건에만 안 쓰는 것(설정 여지), 무음이면 버저 자체가 없음.
