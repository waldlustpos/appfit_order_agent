주문 접수(order intake) 흐름에 대한 사용자의 핵심 관심사: 현재 설계가 과도해서(over-engineered) 불필요하게 복잡해진 상태인지 진단하고, **더 단순한 설계가 가능한 여지**를 평가하는 것. 이것이 향후 order-flow 워크플로의 1순위 목표.

레이스 컨디션(자동접수 race / 상태 다운그레이드 / WebSocket·폴링 이중 소스 / 캐시 매니저)은 그 자체가 목적이 아니라 **복잡도의 증상/증거**로 다루고, 동시에 "어떤 단순 대안이든 보존해야 할 불변식(레이스 안전성)"으로도 취급할 것.

**Why:** 사용자가 접수 흐름을 이 프로젝트의 핵심으로 보고 있고, 단순화 여지 평가를 명시적으로 최우선 목표로 지정함.

**How to apply:** 산출물은 버그 리스트가 아니라 "복잡도 진단 → 본질적 복잡도 vs 우발적 복잡도 구분 → 단순 설계 대안 평가". 각 복잡 요소마다 "왜 이렇게 됐나 / 꼭 필요한가 / 제거 시 깨지는 불변식은?"을 물을 것. 폴더 구조 재구성(다른 세션 진행 중) 완료 후 **새 구조 기준**으로 실행. 관련: [[feedback_queue_enqueue_timing]]
